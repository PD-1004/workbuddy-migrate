# WorkBuddy 会话迁移助手：用户反馈自查

核查日期：2026-10-09。

## 结论

反馈涉及两件事：不同电脑显示的打包选项不同；重复迁移不能带入已有会话及其产出文件的后续变化。这份 EXE 中确实存在对应的实现原因。第二件事已用原始核心字节码和临时数据复现；第一件事已核实两套界面的功能差异，并模拟复现了界面降级分支。尚不能断定反馈者当时具体触发了哪个分支。

## 反馈是什么意思

原话的“完成迁移”可能是“完整迁移”的笔误。结合实际界面，最合理的理解是：某些电脑只能全部打包，另一些电脑能选账号、勾选部分会话；用户想将持续变化的项目反复搬到另一台电脑，却发现再次导入保留了旧内容。

“项目动态更新的结果”有两种具体含义：已有会话新增的问答；同一项目后来修改或新增的实际文件。测试分别覆盖了这两种情况。

需要区分“项目”和“会话”：网页端的指定打包实际上按账号和会话 ID 选择，工作目录可以被多个会话共用。新电脑的导入页面没有另一个“完整 / 部分导入”开关，范围主要在旧电脑打包时确定。

## 1. 为什么不同电脑可选功能不同

EXE 内置两套界面：

| 界面 | 源机打包能力 |
| --- | --- |
| 网页界面 `wb_ui.html` / `wb_web` | 全部打包；指定账号和会话打包 |
| 简化 Tkinter 界面 `wb_gui` | 只有一键打包；没有账号和会话选择控件 |

程序仅在四个固定的 `C:\Program Files` / `C:\Program Files (x86)` 路径寻找 Edge 和 Chrome。装在用户目录、自定义目录或其他盘的浏览器不在此检测范围。

`wb_web.open_window()` 找不到这几个路径时，会调用系统默认浏览器，然后返回 `None`；`wb_web._run()` 却把 `None` 当作失败，关闭 HTTP 服务，启动简化界面。因此，即使默认浏览器成功打开，也会走降级分支。这不是单纯“没安装浏览器”的问题。

验证：模拟“未检测到 Edge/Chrome，但默认浏览器打开成功”和“默认浏览器打开失败”两种情况，均触发关闭 HTTP 服务和启动简化界面。测试替换了浏览器、服务器和 GUI 的外部动作，实际运行 EXE 原始启动函数的字节码，没有启动真实浏览器。

证据位置：原模块 `wb_web.py:31, 444–445, 503–505, 567–575`；原模块 `wb_gui.py:413–433, 560–584`；提取的 `wb_ui.html:600–611`。

这足以解释同一 EXE 的跨电脑差异，但反馈者也可能用了不同版本，或者把源机与现机页面进行了比较。要锁定其真实触发原因，需要两台电脑的界面、EXE 版本/哈希或启动日志。

## 2. 已有会话的后续更新确实无法迁入

核心 `check_migrate()` 用本机已有的会话 ID 建立集合，只将源机未删除且 ID 不在本机集合内的会话放入 `todo`。不会通过 `updated_at` 或正文内容判断已有会话有没有更新。

`apply_migrate()` 的会话登记、正文拷贝和相关索引拷贝主要遍历 `todo`。工作空间产出文件拷贝遍历 `todo` 加需要修复路径的已有会话，而非全部选中会话。

复现步骤：

1. 源机有会话 A，更新时间 100，正文 v1，产出文件 v1。
2. 首次迁入目标电脑：会话、正文和文件均成功导入。
3. 源机继续同一会话，更新时间变成 200；正文新增回复；修改产出文件并新增一个文件。
4. 重新打包并导入。
5. 程序判定待新增会话为 0；目标仍是更新时间 100 和旧正文、旧文件，新增文件也未出现。

以上分别使用“指定打包”和“全部打包”验证，结果相同。因此反馈中的“选部分就不覆盖”描述了真实现象，但其原因不是部分打包独有的限制：全部打包也不能同步已有会话的更新。

这符合当前“只补缺不覆盖”的会话策略，但如果用户把它当作持续同步工具，就会达不到预期。程序还存在“没有需要处理的内容，本机已是最新”的返回文案；仅凭没有缺失 ID，无法证明本机内容是最新的。

证据位置：原模块 `wb_core.py:886–888, 1181–1182, 1212, 1265, 1281–1283, 1311–1317, 1347`。

## 3. 额外发现：实际文件的覆盖规则不一致

`_copy_tree()` 仅比较文件大小：目标文件不存在或者大小不同，就执行 `copy2`；如果大小相同，直接跳过。没有内容比较。

测试在同一工作目录新增会话 C，让它触发工作空间拷贝后，得到以下结果：

| 文件变化 | 实际结果 |
| --- | --- |
| `result.txt` 从短内容变成长内容 | 旧文件被覆盖 |
| `same-size.txt` 从 `AAAA` 变成 `BBBB` | 大小同为 4 字节，保留 `AAAA` |
| 新增 `new-file.txt` | 成功导入 |
| 已有会话 A 的新增回复 | 仍未导入 |

“全部打包”和“指定打包”结果一致。可见“只补缺不覆盖”对会话正文成立，但并不适用于所有工作空间文件；相同大小也不能代表内容相同。这会让用户体验表现为有些更新出现、有些更新缺失。

证据位置：原模块 `wb_core.py:282–283, 1160–1166, 1347–1359`。

## 修复建议

1. 统一两套界面的打包能力，或让网页模式在默认浏览器中可靠运行；浏览器检测应覆盖实际安装位置。
2. 明确区分“补充迁移”和“更新已有会话”。若要支持更新，必须定义源机较新、本机较新和两端都修改的处理规则，同时更新数据库、正文、索引及产出文件。
3. 文件冲突需采用一致规则，不能用大小相等判断内容相同。覆盖前应备份将被替换的实际文件；当前迁移备份函数只备份数据库及 WAL/SHM。
4. 在当前补缺模式中明确提示“已有 X 条会话被跳过，后续变化不会导入”，避免宣称内容已是最新。

目录内没有源码或 Git 仓库，因此直接检查 PyInstaller 打包内容，提取 Python 3.9 字节码、网页资源、常量和反汇编。没有把反汇编冒充原始源码，也没有修改 EXE。核心迁移测试使用该 EXE 的原始函数，所有写入目标都是临时构造的数据目录，没有操作真实 WorkBuddy 会话。

验证命令：`python audit/reproduce.py`。8 个场景的断言全部通过，命令退出码 0；这里的通过表示确认了上述现有行为，不表示问题已经修复。并未在反馈者电脑或真实 WorkBuddy 应用中完成端到端复现。
